## 0. 执行摘要

**循据 ProofPath** 是一个**证据可核验的政策办事助手**。把政策文件变成有原文证据、可核验的办事结论——上传政策 PDF 或通知，直接问"我符合条件吗、要准备什么"，每一条结论必须附上能在原文中逐字定位的引用；定位不到的结论会被系统强制降级为"原文未明确"，而不是照原样呈现给用户。

**核心承诺**：**模型说的话不算数**。系统可信度不取决于模型这一次的输出，而取决于一个独立于模型的离线引用核验层（`verifier.py`）。这是把"AI 幻觉"从不可控风险变成可拦截事件的工程化设计。

**适配知乎社区的场景价值**：知乎是高密度中文专业问答平台，"我符合 XX 政策吗 / 这条法规什么意思 / 我的情况能申请吗"是常年高频的提问类型。ProofPath 的"结论 + 原文 + 引用核验 + 材料清单"四件套恰好是这类问题**最缺的答案形式**——比匿名网友的"应该是吧"更有用，比 ChatGPT 的"根据你的描述"更可追溯，比律师事务所的"需要面谈"更可负担。本计划书 §5 详述三种可落地的合作形态。

## 1. 项目背景与问题陈述

### 1.1 一类被长期忽略的真实需求

| 用户场景 | 当前解决方式 | 主要痛点 |
|---|---|---|
| 想知道"我硕士毕业 28 岁、社保 8 个月能否申请某市租房补贴" | 搜索引擎 + 知乎答主 + 评论区 | 答案不一、无法验证、可能错过条件 |
| 想整理"申请这个补贴要哪些材料" | 反复读政策原文 + 自己列清单 | 漏看例外条款、版本过时 |
| 想确认"申报系统上某字段怎么填" | 在线客服 / 拨打 12345 | 排队、回复慢、还是不知道对不对 |
| 想验证"某 AI 助手给我的资格判断是否真的依据政策原文" | 没法验证，只能信或不信 | 模型幻觉是结构性风险 |

**共同特征**：用户需要的是**可追溯的"个人化判断 + 原文依据 + 行动清单"**，而不是通识问答或聊天陪伴。

### 1.2 现有方案的不足

- **通用大模型问答**：模型会用流畅语言总结，但引用常编造、版本可能过时、不会主动告知"我这段话其实没在原文里"。
- **垂直办事 App**：每接入一个城市/一项政策都是定制开发；政策更新时数据滞后；用户量小、覆盖窄。
- **人工咨询**：律师/12345/线下窗口——可负担性差、响应慢、对个人场景往往只给方向不给答案。
- **网络论坛（知乎/小红书/微博）**：优质回答存在但分散、版本不明、作者身份不保证；提问者难以"挑对"答案；答主很难对每个人的具体情况都给定制判断。

### 1.3 我们的判断

> 这是一个**结构性问题**：用户的真实需求是"个人化 + 可核验 + 可负担"的三者交集，目前没有任何产品把三者一起做对。
>
> 我们做的是**最关键的一步**——**让模型输出变得可核验**。不论底层模型换成谁（DeepSeek、Claude、未来的某模型），核验层永远在；这是信任的工程化。

## 2. 创作思路

### 2.1 整体策略

**不追求"取代真人"或"接所有办事场景"，而是"在政策文件这一类结构化输入上，让 AI 输出具备可验证性"**。

这是一个**有限目标、可被独立验证、且失败有清晰边界**的工程问题：
- **输入**：政策文件（PDF / TXT）+ 用户问题 + 用户填写的个人资料
- **输出**：条件逐条判断（MET / UNMET / NEEDS_INPUT / UNKNOWN）+ 原文引用 + 材料清单 + 待补充信息
- **约束**：每一处引用必须能在原文里**逐字定位**（NFKC + 零宽字符归一化后），定位不到就把结论降级

### 2.2 关键设计原则

| 原则 | 体现 |
|---|---|
| **信任边界 = 离线确定性的核验层** | `verifier.py` 是纯 Python，不调任何 LLM API；它的行为完全可测、可审计 |
| **引用必须可逐字定位** | 0.85 阈值（LCS 覆盖率）的 PARTIAL 才算"基本一致"；否则 NOT_FOUND |
| **引用过短不算证据** | MIN_QUOTE_CHARS = 6 字符（`"合同"`两个字不能算证据） |
| **复合结论必须每个引用都通过** | "硕士 1500 元，**且**首次申请可追补 3 个月"——只要一条引不到，整条降级 |
| **降级是显式的** | MET/UNMET → UNKNOWN；用户看到的是"原文未明确"而不是"模型说可以" |
| **执行安全分级** | 表单填写按 READ_ONLY / LOCAL_WRITE / SENSITIVE 三级；SENSITIVE 默认拒绝 |
| **可审计的哈希链** | 所有关键事件（解析、降级、字段填写、提交）写入 SHA-256 链式日志 |
| **不编造可信度** | 离线演示用预埋剧本（`ScriptedReasoner`），里面故意埋两条"模型错误"演示拦截；不是 demo 漂漂亮亮，是 demo 让观众**看到系统在模型出错时怎么兜住** |

### 2.3 与常见做法的本质区别

| 常见做法 | 我们的做法 |
|---|---|
| "模型说了应该可以" | "模型建议可以，但**这条引用在原文找不到**，已降级为原文未明确" |
| 在 prompt 里写"请引用原文" | prompt 让模型引用，**且**用离线核验层独立校验 |
| 用 embedding 检索然后让 LLM 自由总结 | BM25 词面检索（用户用词与原文接近时精确命中） + 结构化 JSON 输出 + 引用必须可定位 |
| "为每条引用给个超链接" | 超链接只是入口；我们的核验层会**真去原文里找**这一段，找不到就拒绝展示 |
| 演示 = 跑通一遍流程 | 演示 = 故意埋两个引用错误，看系统怎么拦下（这才是核心价值的证据） |

## 3. 技术方案

### 3.1 总体架构

```
┌─────────────────┐    ┌──────────────────┐    ┌─────────────────┐
│ 用户上传文件     │ →  │ 解析 + 切片       │ →  │ BM25 检索        │
│ (PDF/TXT)       │    │ (pypdf/docling)  │    │ (零外部依赖)     │
│ + 提问 + 资料    │    │ 每片带 page 锚点   │    │ 词面匹配         │
└─────────────────┘    └──────────────────┘    └────────┬────────┘
                                                         │ top-k 片段
                                                         ▼
┌─────────────────┐    ┌──────────────────┐    ┌─────────────────┐
│ 渲染 + 总结     │ ←  │ 引用核验          │ ←  │ DeepSeek 模型    │
│ 逐条判定 +      │    │ (verifier.py)     │    │ 结构化 JSON      │
│ 材料清单 +      │    │ 离线、确定性       │    │ 输出 conditions │
│ 缺失信息        │    │ 任一引用失败       │    │ + citations     │
└─────────────────┘    │ → 整条降级        │    │ + missing_info  │
                        └──────────────────┘    └─────────────────┘
                                  ↑
                                  │ 哈希链写入
                                  │
                        ┌──────────────────┐
                        │ AuditLog         │
                        │ SHA-256 链       │
                        └──────────────────┘
```

### 3.2 核心模块

|---|--:|---|--:|
| `text.py` | 71 | CJK 安全的归一化（NFKC + 零宽字符 + 空白去除）；BM25 分词（拉丁 + 中文 unigram/bigram）；LCS 覆盖率 | 100% |

**整体覆盖率 94%**（1413 / 1493 行；250 个测试）。

### 3.3 关键技术决策

1. **BM25 而非 embedding 检索**
   - 政策问答里用户用词与原文高度重合（"硕士"、"社保"、"年龄不超过 35 周岁"等术语都是政策原文用语）
   - 零外部依赖、无需 GPU/向量库、毫秒级响应
   - 同义改写会漏——但这是**已知边界**，会拒答而非编造（详 §6.2）

2. **NFKC + 零宽字符 + casefold + 空白去除** 四重归一化
   - PDF 抽取常把中文句子内部塞空格；不同编码下"合同"vs"合 同"会判错
   - 测试覆盖 `examples/policy.txt` 等典型输入

3. **结构化 JSON Schema + 提示缓存 + 服务端 fallback**
   - Schema `additionalProperties: false` 保证可解析
   - 系统 prompt 块加 `cache_control: ephemeral` 跨请求复用
   - 模型拒答时服务端自动 fallback 到备用模型

4. **demo 模式内置"故意埋的失败"**（`proofpath/demo.py:scripted_report`）
   - 一条 verdict 引用了不存在的句子（覆盖 11%）
   - 一条 verdict 引用了"合同"两个字（过短）
   - 跑 `proofpath demo` 立即看到：5 条 MET + 1 条 NEEDS_INPUT + **2 条因引用失败被降级为"原文未明确"**
   - 这是项目核心价值的可复现证据，不是营销说辞

5. **执行安全 deny-by-default**
   - 动作按 READ_ONLY / LOCAL_WRITE / SENSITIVE 三级
   - 未知 kind 一律按 SENSITIVE 处理（宁可多问一次，也不要误提交一份政府申请）
   - 涉及支付的字段即使 kind 是 fill 也会自动升级为 SENSITIVE

## 4. 核心设计：模型说的话不算数

这一节是产品理念核心，独立详写。

### 4.1 为什么必须独立核验

LLM 输出的"自信"与"准确"之间没有相关性。模型可以流畅地说"根据原文第 X 页...，硕士每月 1500 元"——即使该页其实没这句话。**用 prompt 约束"请引用原文"只解决了一部分问题**：

- 模型可能**记错**页码（指向错的页）
- 模型可能**改写**措辞（用了"硕士"但实际原文是"硕士研究生"）
- 模型可能**自己补充**信息（看似引用、实则创造）
- 模型可能**截断**长引用（让核验更难）
- 复合结论（"X 且 Y"）的引用只要一条编造，整条结论就站不住

### 4.2 我们的核验流程（离线、确定性、可测）

```python
# 伪代码：verifier.verify_report 的核心
for verdict in report.verdicts:
    for citation in verdict.citations:
        page_text = document.page_text(citation.page)  # 原文按页取
        needle = normalize(citation.quote)              # 归一化
        if len(needle) < MIN_QUOTE_CHARS:               # 过短
            mark TOO_SHORT
        elif needle in normalize(page_text):              # 完全一致
            mark VERIFIED
        elif lcs_coverage >= 0.85:                       # 接近一致
            mark PARTIAL
        else:
            mark NOT_FOUND
    if any(citation不可信) and verdict.status in (MET, UNMET):
        verdict.status = UNKNOWN                         # 整条降级
        verdict.rationale += "[证据核验未通过] ..."
```

### 4.3 三条不可妥协的硬规则

1. **逐字比对，归一化后必须存在**——可放宽度避免误判，但底线是"原文真有这段话"
2. **引用过短不算证据**——`"合同"`两个字能匹配几乎任何政策页
3. **一条结论里只要有一个引用无法定位，整条降级**——拦住"硕士 1500 元**且**首次申请可追补 3 个月"这种半真半假的复合结论

### 4.4 这一设计的工程价值

- **可测**：`tests/test_verifier.py` 完整覆盖 7 个 CitationStatus 与 4 个降级路径
- **可审计**：`tests/test_e_security_adversarial.py` 显式构造编造引用、TOO_SHORT 引用测试拦截
- **可替换**：底层模型从 Anthropic 换到 DeepSeek（已发生），核验层逻辑完全不变
- **可解释**：`proofpath render` 报告里明明白白写"已核验 N / 基本一致 M / 未通过 K"——模型哪里出错、错几次、错在哪个 verdict，全是结构化输出

## 5. 知乎社区场景适配

> **本节内容是应用场景与扩展方向，不是已实现功能**。项目当前**未与知乎平台做任何集成**；本节阐述 ProofPath 与知乎问答生态结合的潜在价值与三种可落地的合作形态。

### 5.1 知乎上的相关提问

按搜索词频与提问密度估算，知乎上有大量"政策类 + 个人情境"的问题：

| 类型 | 典型问题示例 | 当前回答形式 |
|---|---|---|
| 资格类 | "我是 XX 学历/年龄/户籍，能否申请 XX 补贴？" | 答主基于自身经验，可能不适用于提问者 |
| 解读类 | "XX 政策第 X 条具体什么意思？满足哪些条件适用？" | 答主引用条款，但版本可能过时或记错 |
| 材料类 | "申请这个要哪些材料？先后顺序是什么？" | 答主列清单，但可能漏看子条件 |
| 比较类 | "A 政策和 B 政策哪个更适合我这种情况？" | 答主基于粗略印象比较，缺乏个人化判断 |

**这四类问题恰好都是 ProofPath 的核心能力域**——输入（政策原文 + 个人情况）→ 输出（逐条判断 + 原文引用 + 材料清单 + 缺失信息）。

### 5.2 知乎用户为什么需要"可核验"的答案

知乎的传统优势是"实名 + 经历式回答"：答主往往说自己"申请过"、"了解过"，读者根据答主背景判断可信度。

但"政策 + 个人"类问题对这种模式构成**结构性挑战**：

- 答主**个人经验** ≠ 政策原文；他的"我申请通过了"是个人事实，但"你也能"是推断
- 答主**可能记错条款**——尤其是有时间跨度的政策
- 答主**无法穷举**所有例外条款（"博士学位年龄放宽到 40 周岁"这种子条件）
- 读者**无法验证**答主引用是否真在原文里

ProofPath 提供的是**与答主经验互补的另一种答案形态**：

| 答主经验式回答 | ProofPath 风格 |
|---|---|
| "我当年是 XX 情况，申请通过了" | "按政策原文第 X 页第 Y 条，XX 条件 MET；引用：'...原文逐字片段...'" |
| "应该需要这些材料" | "材料清单：1. xxx (第 X 页)；2. yyy (第 Y 页)" |
| "具体你得问 12345" | "信息不足，需补充：[社保连续缴纳月数、户籍地址等]" |
| 答主可能记错 | 引用核验层拒绝展示无法定位的引用 |
| 答主覆盖的子条件有限 | 原文每条子条件都拆开判（MET / UNMET / UNKNOWN） |

### 5.3 三种可落地的合作形态

**形态 A：知乎站内"问题补充回答"——ProofPath 链接到答案底部**

- 用户在知乎问"我硕士 28 岁能否申请 XX 租房补贴"
- 答主给出经验式回答（保留知乎特色）
- 答案底部或评论区加一个「用 ProofPath 核验」按钮 → 跳转到 `yyl66624.github.io/-ProofPath/?q=...&profile=...`（已预填问题与个人情况）
- 访问者得到：**答主经验 + 原文逐字引用 + 核验可信度**

**形态 B：知乎专栏 / 圆桌 —「循据回答」专题**

- 知乎「法律」「职场」「城市」等话题下设"循据回答"专题
- 答主以"循据回答"格式写作：经验 + 原文片段 + ProofPath 链接
- 专题对答案有最低要求：每条结论附原文出处、核验状态

**形态 C：知乎机构号（街道/园区/律所等）的内容工具**

- 知乎的机构号（政府窗口、园区运营、律所等）需要持续输出政策解读
- ProofPath 帮它们快速生成"原文 + 引用 + 个人化建议"草稿
- 知乎读者得到更可信的内容；机构号降低编辑成本

### 5.4 适配知乎的工程考量

如果真要做形态 A 或 B，下面是技术上需要补的几块——当前 ProofPath 都没做：

1. **用户授权与隐私** —— 用户在 ProofPath 上传的文件、问题、profile 不能用于训练；如对接知乎需要明确数据流
2. **政策库建设** —— 当前 `examples/policy.txt` 只有一份示例；要做"知乎可调用的政策服务"需要先把若干城市的常见政策入库
3. **同义改写检索** —— 知乎用户的提问往往口语化（"我这种情况能申请吗"），BM25 词面匹配会漏；需要做查询改写或加 embedding
4. **答案质量评估** —— 需要在真实知乎场景里做用户反馈闭环（点赞率、追问率、争议率），不能只看客观核验通过率
5. **多政策冲突时的取舍** —— 同一城市不同区县政策可能冲突；需要按用户地域定位

### 5.5 与知乎现有产品的关系

| 知乎产品 | 与 ProofPath 的关系 | 协同方向 |
|---|---|---|
| 知乎问答 | 现有回答 | 补充"循据回答"作为新格式 |
| 知乎专栏 | 长文 | 答主用 ProofPath 工具生成"原文 + 引用"草稿 |
| 知乎热榜 | 流量入口 | 政策类热门问题展示"循据回答"链接 |
| 知乎机构号 | 内容生产 | 提供辅助工具 |
| 知乎直答 | AI 问答 | 核验思路可借鉴（ProofPath 同样开源） |

**重点说明**：ProofPath 与知乎直答（HiZhan Da）是**互补而非竞争**。知乎直答是大语言模型驱动的开放问答，覆盖面广；ProofPath 专注"政策文件 + 个人情况"这一垂类，强调引用可核验。两者可以并存——读者在知乎直答得到"通识回答"，在 ProofPath 得到"针对你这份政策原文的、可核验的判断"。

### 6.3 没做但常被误以为做了的事

> 这是为了**避免下游误用**——参赛评审、外部开发者、潜在合作方在判断项目能力时，可能从模块名/界面推测出并不存在的能力。

- ❌ **OCR 集成**：`pip install -e ".[docling]"` 后才支持扫描件；**没装时**会明确报错
- ❌ **实时语音交互**：仓库无相关代码
- ❌ **多租户隔离**：当前是单机单用户模型
- ❌ **跨政策联合判断**：当前一次分析一个文档
- ❌ **法规版本变更跟踪**：当前文档内容由用户上传，不自动同步官方发布
- ❌ **付费/真实提交**：明确写在 README——首版不执行真实申请提交、付款或删除
