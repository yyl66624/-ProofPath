## D-001 本地目录从压缩快照转为真正的工作副本（2026年9月13日）

**背景**：`E:\-ProofPath-main` 下原本没有 `.git`，是远端 `main`（`c3f723a`）的压缩快照，无法建分支、开 PR 或配置保护规则。

**决策**：在原目录执行 `git init -b main`、`git remote add origin …`、`git fetch origin main`，再用 `git reset --mixed origin/main` 让索引对齐远端提交。不执行任何覆盖工作区的操作，不重新下载文件。

**理由**：保留现有资产与本地环境；`--mixed` 不改动工作区文件，风险最低。

**验证**：对齐后 `git status` 只剩新增分工文档为未跟踪文件，其余全部干净——这同时证明本地快照与远端 `main` 内容一致。

**影响**：所有后续工作都在真实仓库中进行；`.venv/`、`.pytest_cache/`、`.coverage` 已被 `.gitignore` 覆盖，不入库。

## D-002 换行符统一为 LF（2026年9月13日）

**背景**：团队在 Windows 上开发，机器级 `core.autocrlf=true`。缺少 `.gitattributes` 时，Windows 检出的每个文本文件都与仓库 blob 不同，跨平台 diff 会出现整文件级噪声，也容易让人误判"所有文件都被改动"。

**决策**：新增 `.gitattributes`，文本文件 `* text=auto eol=lf`，图片与 Office 文档标记为 binary。

**理由**：仓库现有文件已是 LF，此策略不产生额外改动；CI 同时跑 Linux 与 Windows，统一行尾可避免两端表现不一致。

**影响**：新增文本文件一律以 LF 入库；如有人需要 CRLF 本地检出，用个人 `core.autocrlf` 配置解决，不改仓库策略。

## D-003 提交身份使用 GitHub noreply 邮箱（2026年9月13日）

**背景**：本机全局 `user.name` / `user.email` 是占位文本（"您的GitHub用户名"），直接提交会产生无法归属、也无法被 GitHub 识别的记录。

**决策**：在仓库局部配置 `user.name=yyl66624`、`user.email=298259411+yyl66624@users.noreply.github.com`。其余成员克隆后各自配置自己的身份。

**理由**：仓库局部配置不污染成员本机全局设置；noreply 邮箱能把提交归属到账号，同时不公开真实邮箱。

**影响**：后续所有提交按账号归属；历史提交（`c3f723a`）不受影响。

## D-004 评审与分支保护采用"管理员可兜底合并"（2026年9月13日）

**背景**：0 号文件 5.2 要求默认分支保持可运行、每个 PR 需审查。但当前仓库只有一名协作者，若强制"禁止管理员绕过"，在只有一人具备合并权限时会让仓库无法推进。

**决策**：启用分支保护——必须走 PR、必须 1 个批准、新提交须驳回旧批准、必须解决会话、禁止强推与删除分支、必须通过状态检查；同时保持"允许管理员绕过"（`enforce_admins=false`）。

**理由**：规则对普通推送生效，同时保留赛事现场可用的应急通道。

**替代方案**：成员全部加入协作者并稳定后，改为 `enforce_admins=true`，取消兜底。

**影响**：管理员能用兜底方式合并，但每次使用都应在 PR 里写明原因。

## D-005 任务看板采用 Issues + 里程碑 + 状态标签（2026年9月13日）

**背景**：0 号文件 5.3 要求任务状态统一为待澄清／可开始／进行中／待审查／待验收／已完成／阻塞，5.1 要求任务进度以仓库任务或看板为准。GitHub Projects（v2）需要 `project` 授权范围，当前凭据没有该范围。

**决策**：以仓库 Issues 承载任务与缺陷，配合七个状态标签与 G0–G5 里程碑使用；不创建 Projects 看板。

**理由**：Issues + 标签 + 里程碑同样满足"任务进度以仓库任务为准"，且不需要额外授权；现有凭据即可维护。

**差距记录**（0 号文件 5.2 允许的替代做法）：缺少跨工作包的看板视图。若需要可视化看板，由管理员执行一次 `gh auth refresh -s project` 后即可补建。

## D-006 CI 采用三作业矩阵：Linux 主验证、Windows 兼容、Python 版本下限（2026年9月13日）

**背景**：仓库此前没有任何自动检查，"我本机能跑"不能作为合并依据；团队在 Windows 开发，部署与展示环境尚未确定（项目卡待填）。

**决策**：新增 `.github/workflows/ci.yml`，三个作业：`pytest-ubuntu`（ubuntu-latest，Python 3.13，带覆盖率）、`pytest-windows`（windows-latest，Python 3.13）、`pytest-python-floor`（ubuntu-latest，Python 3.11，验证 `requires-python` 下限）。

**理由**：Linux 作业承担主要验证，Windows 作业覆盖团队日常环境，下限作业防止依赖声明与实际可用版本脱节。覆盖率只用于发现测试空白，不设统一百分比门槛（0 号文件 9.4）。

**已知限制**：2026年9月13日的本地复验只覆盖 Windows + Python 3.13；Linux 与 3.11 两条作业需在首次运行后确认，若失败应先修正或收窄矩阵，不得直接放宽门槛。

**替代方案**：若后续确定单一目标环境，可把矩阵收窄为一个作业，但需在交付报告中说明放弃的平台及其影响。

## D-007 自动化工作流文件受凭据范围限制（2026年9月13日）

**背景**：推送 `.github/workflows/` 下的文件需要 `workflow` 授权范围，当前 `gh` 凭据的范围为 `gist, read:org, repo`，不含 `workflow`。

**决策**：

1. 先推送不含工作流文件的治理提交，保证仓库其它改进不被阻塞。
2. 工作流文件保留在工作副本中，待管理员执行 `gh auth refresh -s workflow` 后单独提交。
3. 分支保护的必需状态检查在 CI 工作流真正落地后再启用，避免出现"PR 永远等不到检查"的死锁。

**理由**：不因为一个授权范围让整批治理工作停摆，同时避免把必需检查配置成永远不会运行的作业。

**影响**：在工作流落地之前，合并依据是本地实际执行结果与审查记录，而非 CI。
