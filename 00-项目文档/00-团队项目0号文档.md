## 二 当前基础与事实边界

截至本文编写时，本地目录已经包含 ProofPath 的 README、Python 项目配置、源码、示例和测试目录。因此后续工作应先盘点并复用现有资产，不把本项目当作空仓库重新覆盖。

根据当前 README，已有设计包括文档解析、检索、模型判断、引用定位核验、动作风险分级、审计日志及离线演示。README 同时明确：浏览器执行器尚未接入，当前表单计划仅用于演练。本文只阅读了说明与目录，没有重新运行测试，也没有据此确认每项实现都可用。README 所述测试数量和覆盖率不得直接作为本轮验收证据。

此前推荐的开源组件可进入候选清单，但先前给出的精确评分缺乏完整采集和计算证据，本方案不采用这些分数作为选型结论。安装成功、项目星标和存在发布版本，都不能代替本项目的集成验证。

另有两个需要明确的技术边界：

- 引用能在原文中定位，只证明这段文字存在；它并不自动证明推理正确、条件完整、版本有效或用户确实符合资格。因此测试必须加入真实引用支撑错误结论、遗漏例外条款等情况。
- 哈希链可以在特定条件下发现日志修改，但仅凭本地哈希链无法证明日志未被整体重写或尾部截断。Demo 应准确说明其检测范围，不能宣称不可篡改。

## 三 产品定位与 Demo 范围

### 3.1 推荐定位

ProofPath 帮助用户把一份政策或通知转成带出处的条件判断和材料清单，并清楚显示信息缺失与证据不足的位置。在比赛允许且时间充足时，再增加测试网页的辅助填表。

首版只选一个有代表性的申请场景。优先选规则可公开查证、能准备脱敏样例、可以设计正常与异常测试的场景。目标用户是否需要这一工具仍需调研验证，不能把产品构想当作已证实的需求。

### 3.2 核心用户故事

“作为申请人，我希望上传通知并补充自己的情况，看到逐项条件、所需材料和原文出处；缺少信息时，系统告诉我需要补充什么，以便我知道下一步如何准备。”

### 3.3 功能边界

| 优先级 | 功能 | 验收要点 |
|---|---|---|
| 必须 | 上传支持的文本 PDF 或文本文件 | 成功、格式不支持、无可抽取文本均有明确反馈 |
| 必须 | 输入问题和必要的用户资料 | 缺少条件时提示补充，不擅自推测 |
| 必须 | 条件清单与初步判断 | 分开显示满足、不满足、信息不足和证据不足 |
| 必须 | 原文引用与定位 | 能打开对应片段；可疑引用不能显示为已验证 |
| 必须 | 材料清单与结果查看 | 每项说明来源或用户输入依据；支持返回修改资料 |
| 必须 | 一套完整正常流程和异常流程 | 能复现，并有独立测试记录 |
| 可选 | 受控网页辅助填表 | 字段来源可追溯，确认前不能提交 |
| 可选 | 扫描件 OCR 与更多文档格式 | 单独验证准确率、速度及依赖体积 |
| 延后 | 实时语音、多网站自动办理、长期监控 | 不计入首版承诺 |
| 不在首版 | 最终资格认定、真实付款、无人值守申请提交 | 不作为 Demo 能力宣传 |

默认把辅助填表放在扩展阶段。若赛事明确要求 Agent 操作能力，可将其提升为必须项，同时削减其他扩展功能。赛前冻结后，新增功能必须同时提出需要删减的工作。

### 3.4 演示要表达的价值

演示需要让观众看见三件事：用户少做了哪些查找和整理工作；结论如何追溯到原文；系统遇到缺失信息或错误引用时如何处理。节省时间、准确率与获奖概率均不得先写成既成事实，应通过对照任务和实际测量再报告。

## 四 团队分工与决策权限

采用角色分工，不假定需要同等数量的成员。每个工作包只有一位最终负责人；一个人可以兼任多个角色，但关键改动应由另一人或独立审查轮次检查。

| 角色 | 主要责任 | 必须交付 | 决策边界 |
|---|---|---|---|
| 项目负责人 | 赛题、目标用户、优先级、预算和最终验收 | 项目卡、范围确认、发布决定 | 决定重大范围调整与最终发布 |
| 技术统筹与 Codex | 拆解任务、接口协调、集成、开发和测试组织 | 工作包、依赖关系、集成版本、进度报告 | 可推进已授权范围内的实现与验证 |
| 调研与产品 | 用户痛点、竞品、赛事要求、验收标准 | 来源记录、场景说明、需求清单 | 提议优先级，不单独扩展范围 |
| 前端与交互 | 页面流程、组件、状态反馈、证据查看 | 可交互页面、联调结果、界面检查记录 | 遵守已约定的数据与接口含义 |
| 后端与模型 | 文档处理、接口、推理核验、错误与日志 | 接口实现、模块测试、运行说明 | 不绕过确认机制或隐式扩大数据使用 |
| 测试与质量 | 测试设计、异常场景、回归和发布评估 | 测试报告、缺陷单、验收意见 | 对未满足发布条件的版本提出阻断 |
| 集成与演示 | 构建、部署、版本记录、演示和回退 | 演示版本、脚本、备份资料 | 按发布条件推进，不掩盖未完成功能 |

两人团队：负责人兼产品、前端和演示；另一位负责后端与集成，Codex 协助各环节，双方交叉验证。三至四人团队：建议分为产品演示、前端、后端、测试集成四条责任线，按人数合并。

Codex 不能替代团队对真实用户的访谈，也不能把自动化审查描述为外部独立审计。启动后可以按独立工作包并行协作，明确目录所有权；公共数据结构、接口协议、依赖配置和主分支合并由技术统筹协调。禁止两个执行者同时修改同一共享文件却没有交接。

## 五 GitHub 协作规则

### 5.1 唯一交付入口

主仓库保存源码、需求、接口约定、测试记录和版本说明。任务进度以仓库任务或看板为准，聊天中的决策应补入对应任务。大体积素材和模型文件放在适合的存储位置，由仓库记录获取方式和版本；真实个人资料及密钥不提交。

本文件保留在根目录下的 `00-项目文档/` 子目录，README 顶部链接到本文件作为团队入口。目录及文件名以 00 开头，便于在按名称排序的视图中优先查找；具体显示顺序取决于页面排序设置，不等同于 GitHub 的独立置顶功能。

### 5.2 分支与合并

- 默认分支保持可运行；采用短周期任务分支，命名包含任务编号与简短主题。
- 每个 PR 对应一个可审核成果，说明用户可见变化、关联任务、测试结果与限制。
- 合并前完成约定检查和审查；不以“我本机能跑”作为唯一依据。
- 冲突由改动负责人结合集成负责人处理，保留他人无关修改，不通过整体覆盖解决。
- 前后端可先按协议分别开发，但必须尽早合并出一条实际端到端流程。
- API 或共享数据结构的变更先更新约定，并同时通知受影响模块负责人。

仓库创建时核对权限和功能支持，再配置合并限制与自动检查。若当前仓库方案不支持所需保护规则，采用指定集成人合并及书面检查记录作为替代，并记录差距。

### 5.3 看板与沟通

任务状态统一为：待澄清、可开始、进行中、待审查、待验收、已完成、阻塞。每位执行者原则上同时承担一个主要开发任务。任务进入阻塞时写清阻塞原因、依赖人和仍可推进的替代工作。

每天至少进行一次短同步；紧张赛程可按工作阶段同步。每次只报告已完成成果及链接、当前阻塞、下一步交付。涉及接口变更、重大缺陷或工期变化时即时更新任务，不等待例会。

## 六 调研与开源选型

调研先解决影响路线的未知项，形成可执行结论后转入实现，不无期限搜集资料。调研结论必须区分外部事实、团队观察和产品假设。

1. 读取赛事官方规则，记录评分维度、限制、提交物、第三方代码声明要求及来源日期。
2. 对目标场景进行小规模需求验证。建议接触三位潜在用户；若无法接触，明确标注访谈未完成，采用任务走查作为有限替代。
3. 比较手工办理、通用问答工具和直接竞品，记录用户仍需做的步骤，而不是只比较功能数量。
4. 针对确实缺少的能力筛选开源组件，核对维护情况、文档、许可、运行要求、成本和集成难度。
5. 对影响主流程的候选做最小验证，再记录采用或放弃的理由。

| 待评估能力 | 候选或现有资产 | 必须回答的问题 |
|---|---|---|
| 文档解析 | 当前解析实现与 Docling 候选 | 当前样例是否需要 OCR；现有方案是否已经足够 |
| 浏览器操作 | Browser Use 候选与现有动作分级逻辑 | 是否能稳定完成受控页面填表；失败如何退出 |
| 实时语音 | LiveKit Agents 候选 | 是否直接服务评分目标；是否挤占核心联调时间 |
| 模型调用 | 当前调用实现及赛事可用服务 | 账号可用性、结构化输出、时延、费用与失败处理 |

选型记录至少包含官方来源、查阅日期、固定版本、许可证、运行要求、验证结果和替代方案。星标仅作为社区关注度信号。引入开源能力时写明上游项目及团队新增贡献；不将上游原有功能包装为团队原创。

## 七 开发框架与接口协作

### 7.1 核心数据流

用户上传文件 → 后端提取原文与位置 → 用户补充资料 → 检索相关条款 → 生成初步判断 → 核验引用与判断依据 → 前端展示结论和证据 → 用户修改信息或整理材料。

扩展流程：结果与资料生成填写计划 → 用户查看字段和值 → 在受控页面执行 → 必要确认 → 返回实际操作结果。

### 7.2 模块边界

- 前端负责输入、进度、结果与证据查看，不自行决定资格状态，也不持有服务端密钥。
- 后端负责请求校验、任务处理和统一状态；长任务的结果必须可区分运行中、失败、取消和完成。
- 文档模块保存可追溯片段及位置，解析失败时返回原因，不能把空内容当作有效文档。
- 推理模块提出判断，核验模块检查引用、支撑关系及条件缺失；对于不能可靠判断的内容保留不确定状态。
- 操作模块与分析模块分离；分析完成并不等于申请已经提交。
- 日志记录必要的处理信息和版本，避免默认保存完整敏感资料。

### 7.3 联调前必须约定的数据

| 对象 | 最少约定字段或含义 |
|---|---|
| 文档 | 文档标识、名称、格式、处理状态、版本或内容摘要 |
| 原文片段 | 片段标识、所属文档、位置、原文；非 PDF 不伪造页码 |
| 用户资料 | 字段、值、来源、未知或未填写状态 |
| 条件判断 | 条件名称、判断状态、理由、证据关联、待补充信息 |
| 材料项 | 名称、是否必需、依据、是否已提供 |
| 分析任务 | 任务标识、状态、结果位置、失败原因 |
| 操作计划 | 目标页面、动作、字段值、来源、确认要求、执行状态 |
| 错误 | 稳定错误标识、用户可读说明、能否重试及建议动作 |

接口约定还需包含请求和响应示例、文件大小上限、超时、重复请求处理、分页或任务查询方式。原文引用采用明确的文档与片段标识，不只返回一段无法定位的文本。前端先用约定样例完成页面，再替换为真实接口；样例数据必须有明确标记。

### 7.4 首轮集成策略

先完成“一个文件、一项问题、一个结果页”的真实流程，再扩展材料清单和复杂状态。模型真实调用与离线预设演示分开记录；如果只有离线流程跑通，只能交付离线演示状态。技术方案尽量复用仓库现有实现，新增框架和依赖需要写明解决的具体问题与成本。

## 八 前端与交互方案

首版采用四个连续步骤，避免同时铺开多个工作台。用户始终知道正在处理哪份文档、当前到了哪一步以及下一步能做什么。

| 页面或步骤 | 内容 | 必须覆盖的状态 |
|---|---|---|
| 文件与问题输入 | 文件上传、问题、演示样例入口 | 初始、上传中、完成、不支持、失败 |
| 资料补充 | 仅询问与条件相关的信息 | 未填、有效、无效、不愿提供、返回修改 |
| 分析结果 | 条件状态、解释、缺失信息、材料清单 | 分析中、成功、部分可用、证据不足、失败 |
| 原文与行动 | 对应原文定位、材料整理；可选填写预览 | 定位成功、定位失败、待确认、取消、执行失败 |

判断状态需要文字与视觉提示共同表达，不只靠红绿颜色。错误提示应指出用户能够采取的动作。加载超过预期时展示实际状态，不伪造完成百分比。重复点击不能导致重复提交或重复付费调用。

前端验收包含：主要展示屏幕无内容遮挡；文本和按钮可读；键盘可完成核心操作；长文件名、长引用和空结果布局正常；成功、失败、取消与返回路径完整。手机适配是否作为必须项，由赛事展示环境决定。

## 九 测试与验收框架

### 9.1 可开始与可完成标准

任务可开始：有负责人、明确输入输出、验收条件、依赖状态和所需权限。任务可完成：成果已纳入目标版本、相关检查通过、已记录限制，且验收人员能依据说明复现。写完代码和提交 PR 均不等于已完成。

### 9.2 分层验证

| 层级 | 重点 | 证据 |
|---|---|---|
| 模块测试 | 文本处理、状态计算、引用核验、风险分类 | 自动化结果与失败样例 |
| 接口测试 | 输入输出、缺失字段、错误状态、超时 | 接口检查记录 |
| 集成测试 | 解析、检索、推理、核验之间的数据一致性 | 固定样例输入输出与版本 |
| 端到端测试 | 从页面上传到原文定位的完整流程 | 可复现步骤、运行记录或录像 |
| 模型质量评估 | 判断正确性、证据支撑、拒答和信息补全 | 人工标注样例与逐项结果 |
| 界面检查 | 状态展示、长内容、可读性和操作路径 | 检查清单与缺陷记录 |
| 运行检查 | 干净环境启动、依赖、耗时与调用成本 | 环境、版本、实测值和限制 |

### 9.3 必须测试的场景

| 编号 | 场景 | 预期行为 |
|---|---|---|
| T01 | 支持的文件与完整资料 | 完成分析，引用能定位，条件解释一致 |
| T02 | 缺少关键用户信息 | 显示待补充内容，不能直接判定满足 |
| T03 | 编造引用或定位失败 | 不呈现为已验证结论，并说明证据问题 |
| T04 | 引用真实但不支持结论 | 识别或降级；结果计入质量评估，不能只测字符串匹配 |
| T05 | 忽略例外条款或多份文件冲突 | 暴露冲突和限制，避免确定性结论 |
| T06 | 扫描件、空文件、损坏或不支持格式 | 明确失败原因和替代操作，无空白成功页 |
| T07 | 模型超时、无权限、额度不足或异常输出 | 可理解错误、保留必要输入，按预算限制重试 |
| T08 | 文档包含诱导系统执行额外指令的文本 | 将其作为文档内容处理，不执行无关操作 |
| T09 | 重复点击、刷新或取消 | 状态可解释，不重复创建外部操作 |
| T10 | 多用户场景下访问他人文档 | 若包含多用户能力，必须验证访问隔离 |
| T11 | 日志、浏览器响应与仓库文件 | 不暴露密钥；检查测试所覆盖的敏感字段 |
| T12 | 可选填表遇到确认、拒绝或网页变化 | 未确认不提交，拒绝后停止，失败如实报告 |

### 9.4 Demo 发布条件

以下是本项目建议采用的内部标准，不是外部行业标准，也不是当前实测结果：

- 固定验收集建议至少包含 20 个案例，覆盖正常、缺失信息、引用问题、规则冲突和运行异常；开发样例与保留验收样例分开。
- 已纳入范围的关键确定性检查全部通过；存在跨用户泄露、未经确认的敏感提交或不可启动问题时不得发布。
- 模型评估报告分开给出条件判断正确率、引用可定位率、证据支撑正确率、应拒答案例处理情况，并给出样本数；小样本成绩不能解释为普遍可靠性。
- 所有模型误判必须分类。对本版目标场景中尚未解决的明确错误，修复或收缩支持范围后再验收，不能仅靠平均分掩盖。
- 目标展示环境连续完成三次核心演示，并走通一次异常恢复；这只证明演示检查通过，不代表生产级稳定性。
- 冻结版本完成一次干净环境复现，实际测试结果与提交版本一致。
- 若主打真实模型服务，必须完成真实链路测试；仅离线样例成功不满足这一声明。

覆盖率作为找测试空白的参考，不设置脱离风险的统一百分比。性能与成本在样例文件大小、设备和模型确定后测量并设定目标；报告端到端耗时、失败情况与单次费用，不先承诺固定秒数。

### 9.5 缺陷处理

阻断缺陷：无法启动、主流程中断、关键数据错误或越权行为，停止发布并优先处理。重要缺陷：核心结果错误、证据误导或主要交互不可用，修复或移出受影响能力后发布。一般缺陷：非核心体验问题，可在不影响演示和用户理解的前提下记录延期。

每个缺陷记录复现条件、预期、实际、版本、负责人和复验结果。开发者修复后由测试角色复验；若同一人兼任，至少另开独立验证轮次，并如实说明。

## 十 从启动到交付的阶段计划

以总可用开发时间为基准分配工作。以下比例为团队排期建议，实际工时由成员投入和截止时间换算，不是完成时间保证。已有原型可减少实现工作，但不能省略资产盘点和版本复验。

| 阶段 | 时间占比 | 主要任务 | 离开阶段的条件 |
|---|---|---|---|
| G0 启动与盘点 | 5% | 项目卡、仓库、权限、现有资产和运行基线 | 清楚已有能力、缺口和负责人 |
| G1 调研与范围 | 10% | 赛题、用户、竞品、MVP 与验收用例 | 一个场景确定，必须项不再模糊 |
| G2 交互与接口 | 10% | 页面流程、数据对象、接口和技术选型验证 | 前后端可以按相同约定工作 |
| G3 开发与首轮集成 | 35% | 模块并行实现、真实端到端流程 | 核心路径跑通，异常处理可见 |
| G4 联调与质量验证 | 20% | 缺陷修复、模型评估、运行与界面检查 | 满足 Demo 发布条件 |
| G5 冻结与交付 | 20% | 固定版本、干净环境复现、路演排练和提交 | 交付清单齐备，演示可复现 |

进入 G5 后默认冻结功能，只修复阻断交付的问题。延期时按顺序削减实时语音、多格式支持、多场景和自动填表等扩展项；保留核心证据展示、失败反馈、测试与交付时间。若自动填表属于赛题必需项，重新调整削减顺序并留下决策记录。

## 十二 运行成本与交付风险

| 风险 | 提前检查 | 对应处理 |
|---|---|---|
| 赛题不匹配或已有代码不符合规则 | 阅读官方规则并记录依据 | 调整场景或复用范围，保留贡献说明 |
| 功能堆积挤压交付时间 | 检查必须项和里程碑 | 先砍扩展功能，保留联调与验收 |
| 模型幻觉或遗漏条件 | 运行保留验收集 | 显示不确定性、补全信息、缩小支持范围 |
| 文档解析效果不足 | 验证目标格式与代表样例 | 明确支持格式；必要时增加 OCR |
| 外部网站变化导致失败 | 在目标环境验证操作 | 首版使用受控页面，明确其演示属性 |
| 模型账号、费用或网络不可用 | 启动时核对服务与预算 | 设置超时和重试上限，准备标记清楚的离线演示 |
| 多人接口不一致 | 尽早约定数据并集成 | 单一接口文档、指定共享模块负责人 |
| 临时环境无法复现 | 固定依赖、记录实际环境 | 冻结前干净环境重建并保留上一稳定版本 |

项目预算至少分为模型调用、托管和存储；记录上限、监控人及超限后的降级方式。共享密钥通过适当的凭据渠道分发，文档只写变量名和配置步骤。使用真实材料前明确授权、存储和清理方式；比赛样例优先采用公开或脱敏资料。

## 十三 Demo 和最终交付

### 13.1 建议演示脚本

默认准备三分钟版本，实际按比赛要求调整：前 20 秒说明用户和问题；随后 50 秒上传文件并补充资料；再用 50 秒展示条件与原文定位，包括一条证据不足的判断；随后 40 秒展示材料清单，或在已完成的情况下展示受控填表；最后 20 秒说明实测结果、团队贡献和当前边界。

现场流程使用事先标明的演示资料。实时调用、缓存结果、离线预设和受控表单必须清楚区分。备份录屏应来自已交付版本，网络失败时明确告知正在切换备份，不能把录像说成实时执行。

### 13.2 最终交付清单

- 主仓库链接与冻结提交标识或版本标签。
- 本 0 号文档及已补齐的项目卡。
- 当前真实能力、已知限制、环境要求和启动说明。
- 前后端接口与关键技术决策说明。
- 脱敏演示资料、数据来源和开源归属说明。
- 与冻结版本对应的测试报告、评估样例数量和未解决缺陷。
- 可访问的 Demo，或赛事接受的本地启动方式。
- 路演脚本、备份录屏和故障回退步骤。
- 实际资源费用记录及需要关闭的临时服务清单。

只有这些交付物与实际版本相符，且必须功能满足验收条件时，才能标记“Demo 完成”。比赛提交、公开部署和主仓库合并按项目负责人已授予的权限执行；权限不足时，先准备好可审阅的具体成果，再处理最后一步。
